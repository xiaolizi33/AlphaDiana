# 问题复盘与修复记录

更新日期：2026-11-17。本文汇总接入、实验、恢复和交付中实际出现的问题。**下列实现与设计错误来自本项目的适配过程，不是论文的已知缺陷。** 历史分数保留，但它们只能支持对应实现和协议下的结论。

当前代码审查见 [IMPLEMENTATION_REVIEW.md](IMPLEMENTATION_REVIEW.md)，运行入口见 [README.md](README.md)。原始请求、逐题结果和完整调试日志在本地交付包中；本仓库包含代码、说明和下方的审计摘要，并未上传全部原始实验数据。

## 1. 最重要的方法一致性问题：深度编号和基线反馈

**发生了什么：** 附件式 A/B/C 入口将基础求解器记为 depth=0，A/B 为 1，C 为 2，并且没有向 Ω 传 `previous_scores`。官方代码使用 base=1、首层=2、第二层=3，且只有 `depth >= 3` 并提供基线分数时才选择 `OMEGA_PROMPT_META`。

**影响：** 历史 C 虽然读取了已有策略和运行轨迹，却没有进入官方的高层诊断提示分支。该问题影响 synthetic pilot、MATH-500 正式 A/B/C 运行、CO-Bench smoke 和资源契约修正后的 CO-Bench A/B/C 对照。此前“流程完成”或“资源限制修正”不能等同于方法已忠实复现，不能据这些结果否定论文方法。

**修复：** 后续生成入口使用官方编号，并传入父策略生效之前的基线分数和当前分数；保存 `upstream_depth`、`baseline_rows_hash`，拒绝用旧编号的父策略继续生成新层。

**验证与剩余工作：** [离线回归测试](../tests/harness/meta_n/test_generation_contract.py)调用真实 OmegaEngine、使用假模型传输，确认 C 进入 depth=3 高层提示。**修复后的附件生成入口尚未重新跑真实端点实验，旧分数不是修复后代码的性能结果。** 直接使用官方 EvolutionaryOrchestrator 的 8k/16k 消融已采用官方编号，不受这项入口问题影响。

## 2. 执行时限没有明确传给模型

**发生了什么：** 初次 CO-Bench smoke 的实际限制为每实例 3 秒，初始 solver/Ω 提示未明确说明。A 生成的 helper 建议运行 4–6 秒，超过了实际限制，导致生成集评分超时。

**影响：** 这是执行环境与生成策略不匹配，不能把这些失败解释成模型缺乏能力或递归无效。该轮只保留为调试证据。

**修复与验证：** [ResourceContract](../alphadiana/harness/meta_n/resource_contract.py)统一生成模型提示和 scorer 配置，修正轮明确每实例 10 秒、helper 合计最多 5 秒，并要求检查内循环耗时及返回可行解。已检查真实请求中的契约和实际 scorer 参数一致；另有[契约回归测试](../tests/harness/meta_n/test_resource_contract.py)。这修复了资源问题，但没有自动修复第 1 项方法偏差。

## 3. 测试划分可能为空

**发生了什么：** 数据预检最初直接取每类的首个官方文件，但部分文件的实例全部属于官方 dev，取 test 补集后没有实例。

**影响：** 若把空评估当作正常 0 分，会把数据选择错误混入方法结果。问题在新增付费运行之前发现。

**修复与验证：** 归档旧预检协议和文件，T 改用含测试实例的官方非 dev 文件；评分器拒绝空评估。修正后的 G/D/T 任务类别互斥。没有依据测试分数换题。

## 4. 官方优化评分不能套用数学答案正确率

**发生了什么：** CO-Bench 要求生成接收实例参数的 `solve(**kwargs)`，返回优化解字典；原 MATH-500 执行器调用的是无参数 `solve()` 并比较答案。

**处理：** 新增 [CO-Bench harness/scorer](../alphadiana/harness/meta_n/co_bench.py)，调用官方 loader、约束检查、归一化评分及 dev/test 索引。预检中无效程序为 0，已知有效的装箱程序得到约 0.988。

**解释边界：** CO-Bench 报告连续归一化质量。通用字段 `correct` 只表示分数大于 0，不能称作“数学题答对”。质量改善/下降也不等同于标准问答的改对/改错。这是需要明确的任务适配差异，不是已修复的算法缺陷。

## 5. 评分进程清理错误与批次总时限

**发生了什么：** macOS 在子进程退出后的进程组清理中抛出 `PermissionError`，使一份已生成程序未能记分。另发现一个官方文件可包含 100 个实例，固定的批次总时限可能不足以覆盖所有实例允许的执行时间。

**修复：** 已退出进程的清理权限错误不再覆盖评估结果；存活进程仍需终止。批次 deadline 按实例数和每实例限制推导。批次基础设施超时、空评估和非有限分数会报错等待审计，不冒充模型质量的 0 分。

**数据处理：** 原始评分失败行没有删除，只重评同一份保存程序，并通过原始行 hash 关联独立的 `score_repairs`。未为此重新调用模型。对应清理和 deadline 逻辑有回归测试。

## 6. 输出截断限制了候选生成

**发生了什么：** 8192 输出上限的消融中，完整搜索分支有 7 次截断，单层分支有 1 次；该轮最高只形成 depth=2，也就是一层策略。

**影响：** 即使该轮 archive-best 有正分差，也不能归因于高层递归，因为并未形成多层候选。

**处理：** 保留该轮全部结果，另立协议，将两分支输出上限统一提高到上游 CLI 默认的 16384，从头独立采样，不挑选两轮中较好的输出替换。16k 轮仍有 1 次截断，未声称截断完全消失；完整分支最多两次执行反馈重试是预先规定的搜索规则，与 SDK 自动重试不同。

**结果：** 16k 轮实际完成 3 轮、13 个 archive 候选，最高 depth=4（三层策略）。递归和四次单层采样的验证 archive-best、best fixed chain 均为 0.991977。本次没有观察到递归优势。两轮的基线也不同，不能把它们的分差全部解释成输出上限变化。

## 7. 恢复脚本误产生一次额外模型调用

**发生了什么：** 恢复代码将原始多行题面与 JSON 转义后的字符串比较，未匹配到已保存的截断响应，因此额外生成了一次输出。

**影响：** 若直接采用这份输出，相当于给某个候选额外采样机会，破坏原定规则。

**修复与审计：** 改为在解码后的 message content 中匹配。原截断仍计 0，额外输出排除出选择和指标，token 与费用仍计入物理用量；修正前文件、request ID 和 hash 均保留。该修正没有改变最佳单层估计量，但改变了对应一次 draw 的均分，不能省略这项历史。

参见[恢复审计摘要](audits/recovery_resolution.json)及[多行匹配回归测试](../tests/harness/meta_n/test_recovery_journal.py)。不能将这段历史表述为“从未重复生成”。

## 8. 请求失败日志可能不完整

**发生了什么：** halt 检查位于日志收尾逻辑之外，阻断请求会留下 `attempt_started`；服务响应缺少 usage 时，异常分支可能没有保存已收到的原始响应。

**修复与验证：** 所有退出路径都结束日志，保存已知响应、usage、预留、异常及网络派发尝试状态，保留原 halt 原因；日志采用临时文件替换。模糊结果不退预留，SDK 不自动重试。见[请求日志回归测试](../tests/harness/meta_n/test_request_journal.py)。派发尝试不等于已确认服务计费，保守预留也不等于账单。

## 9. 本机通过不等于干净环境可复现

**发生了什么：** 早期测试依赖工作区外的 MATH-500 产物。首次独立 checkout 测试还发现，位于临时目录的新 venv 被沙箱的临时目录拒绝规则拦截，Python 无法读取 `pyvenv.cfg`。

**修复：** 测试改用仓库内的合成 fixture；它们不属于正式实验数据。固定 Metaⁿ commit 和依赖版本，沙箱只对白名单运行时目录添加例外，仍禁止读取其他用户文件和临时工作区。

**验证：** [干净环境验证](../scripts/meta_n/verify_clean_checkout.py)重建源码、新建 Python 3.11 venv、安装固定依赖，在没有现有实验目录的情况下通过 32 项测试及 CLI 启动。首次失败和修复后重跑均有记录。这证明工程契约和安装，不证明真实端点上的算法效果。

## 10. 早期调试记录并非从第一步就完整统一

2026-11-17 核查时，资源修复阶段有 34 次统一命令记录，均有 stdout/stderr 和返回码，其中 19 次包含逐次源码副本。新增三组实验的 138 次模型调用与预留 ledger 的 request ID 一一对应。MATH-500 正式实验的 270 条逐题记录均有请求、响应和 usage。

这些证据不能推导出“项目开始以来每条命令、每次源码修改都可完整重放”。缺失历史不补造。后续统一使用 `debug_run.py`，区分原始记录、代码修复、评分修复与事后说明。数字是该次核查的时间切片，不是后续所有调试的累计数。

## 12. 结论与后续规则

1. **流程跑完、资源公平、方法一致、泛化收益是四件不同的事。** 必须分别验证，不能互相替代。
2. 改动 Ω 的深度、分数反馈、提示、数据划分或预算，需要新协议和明确的实现版本；不能把旧分数当成新代码结果。
3. 先检查非空划分、官方评分和资源传递，再进行付费调用；预检成功也不代替方法一致性审查。
4. 恢复优先复用已有输出；任何额外调用都要记录、计费，并明确是否进入指标。
5. 相同候选被两分支选中时，共享测试输出或明确重复调用的波动；不能把波动当作递归收益。
6. archive-best 是按题选最好的验证候选，不等于单条部署策略，更不等于未见题测试结果。
7. 当前样本小、只有一个搜索 seed，且论文式消融两分支实际计算量和采样温度不同。负结果不能否定论文，正向个例也不能证明普遍收益。
8. 本次修复后的附件生成入口尚待真实端点复验。下一轮若开展，应先冻结新协议，保留未参与调参的测试数据，不追逐预设的正结果。

本次仅整理复盘文档与审计摘要，不运行付费实验，不修改历史数值。
